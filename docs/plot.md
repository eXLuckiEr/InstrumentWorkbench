# Графики: `PlotBuffer` и `PlotView`

Один виджет для двух ролей: большой «осциллограф» в центре окна и маленькая «шкала формы
сигнала» рядом со значением или кнопкой. Только Qt Widgets и QPainter, ничего доустанавливать
не нужно.

## Как это устроено

```
сессия (рабочий поток)                       UI-поток
  разбор кадров → QVector<float>  ──postBatch──►  PlotBuffer  ◄── PlotView (полный)
  раз в 10..30 мс, по ряду                        (кольцо +      ◄── PlotView (компактный) × N
                                                   пирамида)
```

* **`PlotBuffer`** хранит историю: кольцо `float` на каждый ряд (ёмкость округляется до степени
  двойки, по умолчанию 1 048 576 отсчётов на ряд) и пирамиду мин/макс (блоки по 16, 256, 4096 ...
  отсчётов). Запрос «мин/макс на диапазоне» стоит сотни операций независимо от длины диапазона.
* **`PlotView`** рисует не точки, а столбцы пикселей: для каждого столбца берёт мин/макс из
  пирамиды и рисует одну вертикальную черту. Стоимость кадра зависит от ширины виджета, а не
  от числа данных, и узкие всплески не теряются. Если в окне меньше ~2 отсчётов на пиксель,
  рисуются настоящие точки, соединённые линией (для SCPI-опроса).
* Кадры строятся не чаще `frameRate` раз в секунду (по умолчанию **60**; компактные графики-«спарклайны» — не более **10**, `setFrameRate()` меняет) и только когда пришли
  данные или изменились настройки: график на паузе или без данных процессор не занимает.

## Два способа рисовать: GPU и CPU

Картинка одна, способов два. Всё, что нужно для кадра (мин/макс по столбцам, оси, подписи,
легенда), считается один раз в `PlotView::buildFrame()`, дальше кадр рисует один из рендереров:

| Рендерер | Как | Когда |
|---|---|---|
| **Gpu** | кривые и сетка это треугольники, которые рисует `QRhiWidget` (Metal на macOS, Direct3D на Windows, Vulkan/OpenGL на Linux); подписи, легенда и рамка остаются на `QPainter` поверх | большой график; 4K и быстрые сигналы почти не увеличивают нагрузку |
| **Cpu** | `QPainter` | маленькие виджеты (компактный режим) и запасной вариант |

`Renderer::Auto` (по умолчанию) = `Cpu`: замеры на macOS показали, что `Gpu` не снижает нагрузку главного потока (Qt пересобирает всё окно вокруг `QRhiWidget`) и стоит ~3× памяти. `Gpu` включается явно (`IWP_PLOT_RENDERER=gpu`, `[plot] renderer=gpu`). Если GPU
недоступен (нет Qt Shader Tools при сборке, нет подходящего графического API, шейдеры не
собрались), виджет сам переходит на `Cpu` и пишет предупреждение в лог.

* Сборка: GPU-путь включается, если CMake нашёл **Qt Shader Tools** (в сообщении при
  конфигурации `PlotView: GPU renderer enabled`). Если модуль не установлен, добавьте его в Qt
  Maintenance Tool (Qt 6.x, Additional Libraries, Qt Shader Tools); без него всё работает на CPU.
  `QRhi` это закрытое API Qt Gui (линкуется `Qt6::GuiPrivate`), совместимость гарантируется
  только для версии Qt, с которой собрано.
* Настройки приложения (`settings.ini` или `iwp.ini`):

  ```ini
  [plot]
  fps=60          ; кадров в секунду; на слабом железе можно 30 или 20
  renderer=auto   ; auto | gpu | cpu
  ```

  Для проверок есть переменные окружения `IWP_PLOT_FPS=30` и `IWP_PLOT_RENDERER=cpu`
  (приоритетнее файла).
* Для конкретного виджета: `setFrameRate(n)`, `setRenderer(...)`, `usesGpu()`.
* Данные для плавных 60 кадров нужно присылать не реже: сессия `telemetry` отправляет пачки
  каждые 16 мс (см. `kPlotPostMs`), значения для остального интерфейса по-прежнему раз в 33 мс.

## Время по оси X

ОС отдаёт байты пачками, поэтому время приёма отдельного отсчёта ничего не значит. Буфер хранит
время **по пачкам** и восстанавливает его:

* `PlotSeriesInfo::regular = true` (по умолчанию): ровный поток. Интервал между отсчётами
  сглаживается по приходам пачек, фаза подтягивается к ним медленно, поэтому форма сигнала не
  «дышит» от дрожания доставки. Первая пачка после старта и после паузы в потоке > 0,5 с
  привязывается к времени прихода.
* `regular = false`: нерегулярные точки (значения, опрошенные по SCPI). Отсчёт получает время
  своего прихода.

Режим оси X у виджета: `Time` (секунды до самого свежего отсчёта) или `Samples` (номер отсчёта,
не зависит ни от каких часов).

## Подключение в плагине устройства

Сессия (конструктор выполняется в UI-потоке):

```cpp
m_plot = model->addPlot("signals");              // буфер принадлежит модели
iwp::PlotSeriesInfo info;
info.name = "DATA1";
info.unit = "V";                                 // необязательно
info.regular = true;                             // false для нерегулярных значений (SCPI)
m_plot->addSeries(info);                         // ряд 0
```

Где угодно в рабочем потоке:

```cpp
m_plot->postBatch(0, std::move(values), iwp::PlotBuffer::now());   // пачкой, 10..30 раз/с
m_plot->postSample(1, float(v));                                   // один нерегулярный отсчёт
m_plot->postClear();                                               // начать историю заново
```

Страница:

```cpp
auto *big = new iwp::PlotView(model->plot("signals"));             // полный режим
big->setWindowSeconds(30);

auto *spark = new iwp::PlotView(model->plot("signals"));           // «шкала» в карточке
spark->setStyle(iwp::PlotView::Style::Compact);
spark->setSeries({0});                                             // только ряд 0
spark->setWindowSeconds(30);
spark->setFixedSize(150, 26);
```

Один буфер можно показывать в нескольких виджетах, у каждого своё окно и набор рядов.

Правило: **в `postBatch` отправляйте пачки, а не отдельные отсчёты быстрого потока**, и не
превращайте каждый кадр в сигнал или в строку `QVariantMap` (см. `telemetrysession.cpp`:
последние значения лежат в массивах и превращаются в карту раз в 33 мс).

## API виджета

| Метод | Что делает |
|---|---|
| `setStyle(Full/Compact)` | оси, сетка, легенда или только кривые |
| `setXAxis(Time/Samples)` | ось X |
| `setWindowSeconds(s)` / `setWindowSamples(n)` | длина окна |
| `setSeries({..})` | какие ряды показывать (пусто = все) |
| `setAutoRange(bool)` / `setRange(lo, hi)` | автомасштаб или фиксированный Y |
| `setPaused(bool)` | заморозить окно, данные продолжают копиться |
| `setFrameRate(n)` / `setRenderer(r)` | частота кадров и способ рисования |

Пока нет: курсоры, масштаб колесом и прокрутка по истории, экспорт. Всё это добавляется поверх
готового кода: данные в буфере уже хранятся.

## Проверка на симуляторе

Транспорт `sim` в режиме `telemetry` понимает (в JSON настройках транспорта):

```json
{"mode": "telemetry", "rate": 100000, "glitch": true, "errorRate": 0.002}
```

* `rate`: кадров в секунду (1..200000, по умолчанию 400). 100000 кадров по 6 каналов это 3,2 МБ/с.
* `glitch`: каждые 3 с в DATA2 попадает одиночный выброс на +8. На графике он должен быть виден
  при любом масштабе: это проверка, что прореживание не теряет пики.
