# CAN / CAN FD

Устройство **CAN-шина** (группа «Инструменты») показывает кадры шины и отправляет свои. Адаптер подключается как
обычный канал («CAN-адаптер»), настройки порта задаются в окне подключения.

## Адаптеры

| Канал | Что это |
|-------|---------|
| `canslcan` — CAN-адаптер (SLCAN, последовательный порт) | USB-CAN с прошивкой SLCAN: на macOS это `/dev/cu.usbmodem…`, на Windows `COMn`, на Linux `/dev/ttyACMn`. Проверялось на логике, на железе CANable 2.0 ещё нет |
| `cansim` — симулятор CAN | без железа: отправленные кадры возвращаются (эхо), генератор выдаёт трафик заданной интенсивности |

Адаптер CANable 2.0 бывает с двумя прошивками. С **SLCAN** он виден как последовательный порт (подходит этот
канал). С **gs_usb / candlelight** это отдельное USB-устройство, порта нет, и этот канал с ним не работает (если порт
не отвечает, программа так и пишет). Перепрошить адаптер в SLCAN можно через веб-обновление прошивки CANable.

### Настройки подключения

| Поле | Ключ | Значение |
|------|------|----------|
| Порт | `port` | список подключённых портов, можно вписать вручную |
| Скорость | `bitrate` | 10k, 20k, 50k, 100k, 125k, 250k, 500k, 1M (пресеты адаптера) |
| CAN FD | `fd` | включает кадры FD |
| Скорость данных FD | `dataBitrate` | 1, 2, 4 или 5 Мбит/с |
| Только приём | `listenOnly` | без подтверждения кадров и без отправки |
| Автоповтор отправки | `autoRetransmit` | выключение шлёт `A0` |
| Доп. команды | `initCommands` | команды адаптера перед открытием, через `;` (для скоростей вне пресетов и т.п.) |

Порядок открытия: `V` (версия) → `C` (закрыть) → `S<n>` (скорость) → `Y<n>` (скорость данных, если FD) → `M1` (если только приём)
→ ваши команды → `O` (открыть). Прошивка CANable 2.0 подтверждает не все команды (на `S6` и `O` она молчит), поэтому отсутствие
ответа ошибкой не считается: ошибка, если команду отклонили (BEL) или если адаптер не прислал вообще ни одного
байта за всё открытие (тогда это не SLCAN).
Коды скоростей FD (`Y1/Y2/Y4/Y5`) соответствуют прошивке CANable 2.0, на вашей версии их стоит проверить.

## Окно монитора

- **Таблица**: №, время (секунды от открытия шины), направление (Rx/Tx, отправленные синим), флаги
  (STD/EXT, FD, BRS, ESI, RTR, ERR), ID, DLC (для FD с длиной больше 8 в скобках число байт), данные, ASCII,
  интервал до предыдущего кадра. Ctrl+C копирует выбранные кадры строками `ID#ДАННЫЕ`: их можно вставить
  в последовательность.
- **По ID**: одна строка на ID с последними данными, счётчиком и периодом. Для нескольких моторов на шине
  удобнее потока.
- **Фильтр по ID**: `123, 100-1FF, 7E0:7F0, !7FF` (ID, диапазон, ID:маска, `!` исключает). Фильтр меняется
  задним числом: буфер хранит все кадры (до 100 000, старые вытесняются, память не растёт).
- **Пауза** замораживает таблицу, кадры продолжают собираться. **Сохранить трассу**: журнал `candump -l`
  (`(12.345678) can0 123#DEADBEEF`) или CSV.
- Внизу: подключение, счётчики Rx/Tx, кадров в секунду, **нагрузка шины** (оценка без стаффинг-битов).

### Отправка

Тип кадра (стандартный 11 бит / расширенный 29 бит), ID в hex, флаги FD/BRS/RTR, данные в hex
(`30 01 02`, `300102`, `0x30,0x01`), «Повторять каждые N мс». Если ID больше 7FF, тип переключится на расширенный.
Длина проверяется: классический CAN до 8 байт, FD 0–8, 12, 16, 20, 24, 32, 48, 64.

### Последовательность кадров

Поле для списка кадров, по одному в строке (формат `can-utils`), как для SCPI-блоков в консоли:

```
# комментарий
001#30             стандартный ID 001, данные 30
18FF0001#0102      расширенный ID (8 цифр)
7E0#R              удалённый кадр (#R4 = DLC 4)
123##1 00 11 22    CAN FD, цифра после ##: 1 = BRS, 2 = ESI
wait 100           пауза 100 мс (sleep / delay тоже)
```

ID из 1–3 цифр это стандартный, из 4–8 расширенный. Между кадрами добавляется пауза из поля
«Пауза между кадрами» (по умолчанию 10 мс). **Загрузить файл** читает такой список из файла; текст
последовательности и поля отправки запоминаются между запусками.

## Устройство

- Роль `bus` вида `can`; хост менять не нужно: канал приходит из плагина (`IEndpointFactory`, вид `can`).
- Ядро без Qt: `sdk/include/iwp/cancore.h` (кадр, DLC, текст кадра, последовательность, фильтр),
  `plugins/endpoint/canslcan/slcancodec.h` (протокол SLCAN). Тест: `tools/cancore_test.cpp`
  (запускается в CI).
- Новый адаптер (SocketCAN, gs_usb, PCAN…): наследник `iwp::CanEndpoint` (`sdk/include/iwp/canendpoint.h`),
  нужно реализовать `doOpen`, `doClose`, `writeFrame` и звать `deliver(frame)` для принятых кадров.
- Метки времени ставит программа при получении кадра (адаптер времени не присылает), точность порядка
  миллисекунды.

## Ограничения

- Только CAN: протоколов поверх него (CANopen, J1939, MKS SERVO) пока нет, кадры вводятся вручную.
- Счётчики и скорость кадров считаются по тому, что принято программой; потери в адаптере не видны.
- Если кадры идут быстрее, чем таблица может показывать, лишние не попадают в таблицу (счётчик
  «не показано»), в статистику они входят.
